# Phone push notifications: design and split of work

Owner decision, 11 October 2026: **"Phone push"** is the channel for staff whose StockFlow app is closed. This reverses the "No browser push" line in `docs/ORDER-NOTIFICATIONS.md` for this channel only. There is still no email, WhatsApp or SMS, and no paid provider.

Author: Claude Code ("instrument eco development" session). The backend parts below are proposed for ChatGPT / Codex, who owns the notification backend, migrations, secrets and deployment.

## What staff experience

- In the bell, a **"Get alerts on this phone"** switch. Permission is requested only when the person taps it, never on page load.
- After enabling it, a hand-off for their role or an assignment to them shows as a normal phone notification, even when StockFlow is closed. Example: **"Care Hospital · SF-26-1043 — Packed · ready for Tally billing"**. Tapping it opens StockFlow on that exact order. If they no longer have access, they get the plain "not available to you" message.
- While StockFlow is open, the in-app banner still appears. The phone notification uses a per-order tag, so repeats replace each other instead of piling up.
- **iPhone:** works only after "Add to Home Screen" (iOS 16.4+). The switch shows a short install hint on iPhone Safari.
- **Shared phones:** signing out or switching account removes the phone's subscription for the previous person.

## Who gets a push (same rules as the in-app notifications)

| Event (from `private.stockflow_order_events`) | Recipients |
| --- | --- |
| Order enters `awaiting_confirmation` | Administrator, Management, Sales with access to the order |
| Order confirmed (enters pick & pack) | Warehouse, Operations |
| `packed → awaiting_tally_billing` | Accounts |
| Billed in Tally (enters dispatch) | Operations |
| Assignment to a person | The new assignee |

Rules:
- Computed **server-side**, and rechecked at send time against active membership and the existing order-access predicate.
- Follows the role-work contract in `docs/ORDER-NOTIFICATIONS.md`: a person is not pushed about the stage they just completed, but a **combined-role person does receive their own next-role task**. For example, a warehouse+accounts user who packs an order gets the billing hand-off. There is no blanket exclusion of the event's actor.
- One push per (event, person); combined roles do not duplicate.
- Pushes go only for events after the activation time, so turning push on does not trigger a flood of old events.

## Lock-screen content (privacy)

- Payload: { title, body, orderId, orderNumber, customerName }. The order ID is used only to open the order through the normal access-checked path.
- **No amounts, invoice, product or GP data.**
- **Customer name: shown** (owner decision, 11 Oct 2026: "customer name should be visible"). Title <customer> · <order number>, body = the action, e.g. **Care Hospital · SF-26-1043** / *Packed · ready for Tally billing*.

## Architecture (proposed)

1. **Subscriptions:** a new table `private.stockflow_push_subscriptions`.
   - Columns: member email, endpoint (unique), p256dh and auth keys, user agent label, created/last-success/last-failure times.
   - Endpoints are secrets. They are never returned to clients.
   - Rows are deleted when the push service answers 404/410, and on explicit unsubscribe.
   - A unique endpoint means a new account on the same phone replaces the old owner.
2. **API:** a new route `app/api/push-subscription/route.ts` behind the existing staff-session gateway.
   - `GET` → `{ enabled, publicKey }`.
   - `POST` takes the subscription JSON and upserts it for the session user.
   - `DELETE` takes the endpoint and removes it, only for the session user.
3. **Delivery log:** `private.stockflow_push_deliveries (event_id, recipient_email, endpoint_hash, status, attempts, last_error, sent_at)`, with primary key (event_id, recipient_email, endpoint_hash). This gives no duplicates, bounded retries and an audit trail. It never copies customer, financial or invoice data.
4. **Sender:**
   - A once-a-minute `pg_cron` job, using `pg_net`, calls a new Supabase edge function `stockflow-push`. Both extensions are available but not installed on acceptance.
   - Each run, the function sweeps events since the activation time, using a deterministic `created_at, id` window and the delivery log rather than an ID cursor. It applies the recipient policy (one SQL policy function, shared with the in-app event feed), sends, and records results.
   - Order commands never wait on push and never fail because of it.
5. **Crypto:** VAPID (ES256) and aes128gcm payload encryption from a vetted Web Push library that runs on Deno, checked against RFC 8291 test vectors. Do not hand-roll it.
6. **Secrets:**
   - A separate VAPID key pair per environment, generated by Codex or the owner.
   - The private key lives only in edge-function secrets; never in the repo, chat or client bundle. Only the public key is served by `GET /api/push-subscription`.
7. **Switch:** add `push_enabled` and `push_starts_at` to the planned `stockflow_order_notification_config`. Turning push off stops the sweep; subscriptions remain.

## Client side (Claude, this change)

- `public/sw.js`: `push` handler (always shows a notification; per-order `tag`) and `notificationclick` handler. The click focuses an open StockFlow window and posts a same-origin `stockflow-open-order` message, or opens `/?openOrder=<id>&n=<number>`.
- The frame parses that deep link or message into the existing exact-order opening.
- `lib/push-subscription.ts`: support and permission detection, subscribe and unsubscribe through `/api/push-subscription`, and unsubscribe on sign-out or account switch.
- Bell: a "Phone alerts" control with states unsupported / needs Home Screen (iPhone) / off / on / blocked / server not ready. It stays hidden until `GET /api/push-subscription` reports `enabled: true`. Until the backend exists, nothing changes for staff.

## Conditions before push is switched on (from the pre-push review, 11 Oct 2026)
1. **Shared-device cleanup must be guaranteed, not best-effort.** Today `disablePush()` swallows unsubscribe and DELETE failures, and sign-out does not await it. Before activation:
   - sign-out awaits cleanup with a short timeout;
   - a failed server DELETE is retried at the next sign-in on that device;
   - the server also removes a subscription when a different account registers the same endpoint.
2. **Notification taps on standalone pages.** The service worker posts `stockflow-open-order` to the first top-level StockFlow window. A standalone or sign-in page has no listener, so the tap is lost. Before activation: target only windows that acknowledge the message, or fall back to opening the deep link.
3. The client stays dormant until `GET /api/push-subscription` returns `enabled: true` (currently true by design).

## Acceptance checks

- Android Chrome and installed iPhone app: enable, receive a push for each hand-off role with the app closed, tap to open the exact order, deny and blocked states.
- No push for your own action. One push per event per person per phone. A combined-role person gets one push.
- Access removed → no push, and an old notification tap fails closed.
- Sign-out or account switch → the old subscription is removed server-side. A 410 deletes the row.
- The sweep is idempotent under concurrency and retries; disabled config sends nothing; order commands are unaffected when push is unavailable.
- No private key in repo or bundle (`git grep`, built-bundle scan).
