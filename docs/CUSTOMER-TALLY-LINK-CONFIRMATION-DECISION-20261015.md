# Decision: person-confirmed customer–Tally links

**RESTORED by the owner's latest direction on 15 October 2026:** continue this one-time confirmation design and allow new customers for visits without a ledger. This supersedes the intervening withdrawal recorded in [the Tally-authority note](TALLY-AUTHORITATIVE-CUSTOMERS-DECISION-20261015.md). Confirm once; subsequent sales use the stable company/ledger identity, without routine repeated matching. Implementation and release evidence: [current handover](HANDOVER-CUSTOMER-TALLY-LINKS-20261015.md).

Addition: Sales, Operations, Management and Administrator can create a customer in the existing master with a name and optional town/phone, then record visits and contacts before a ledger exists. Do not manufacture a Tally key, balance, revenue or class. Reject an existing active customer name visibly and keep uncertain submissions on the same command key. When an exact ledger later appears in the actual Tally customer export, retain the visit customer rather than importing a duplicate; Management/Administrator confirm its canonical GUID once. Accepted GUID evidence must preserve that UUID and related history across a rename. Nonexact or conflicting records require explicit technical reconciliation; V1 must not merge histories or guess from similar names.

15 October 2026. Codex integration decision under the owner's directive item 3: **approve a Management/Administrator screen for batch person confirmation**, with the following small scope. This is approval to implement the screen, not automatic confirmation of any customer.

- Reuse the existing Customer master and verified Economics customer-identity authority. Do not create a second customer master or a Market-only identity table.
- Suggest only unique exact ledger-master matches from one accepted canonical company/export: the existing customer `tally_key` matches the ledger name, and that same export supplies its canonical ledger GUID. Name equality is a suggestion, not verification. No fuzzy or cross-company match, orphan ID, duplicate name/GUID or conflicting existing binding may be silently selected.
- Show customer name, Tally ledger name, canonical company and ledger GUID, current binding/conflict and export freshness. Searchable, paginated; select individual rows and **Confirm selected**. Do not preselect all or silently include hidden pages. Keep the user flow short.
- Each batch requires an explicit person action and reason. Server verifies the actor's current Management/Administrator role, canonical export/version and each row's expected binding version. Lock deterministically and commit confirmed rows plus audit/events/idempotent receipt atomically. A stale/conflicting row fails the batch visibly; reload without silently dropping it or applying an ambiguous partial batch. Existing shared identity authorization must be preserved; report any incompatible role contract before changing it.
- Repeated identical commands replay their stored result. Changing content with the same command ID is rejected. Record who confirmed, when, exact source company/ledger GUID and evidence generation; never overwrite old audit. Corrections follow the existing governed identity-change path.
- No automatic name-based writes, financial-history re-import, relabelling of complete coverage or class activation. Person confirmation cannot turn incomplete sales or unverified amounts into trusted class figures.

Acceptance: two exact matches can be person-confirmed together once; duplicate/fuzzy/cross-company/stale/export-changed/conflicting rows fail without partial writes; Sales/Viewer writes are denied; replay creates no duplicate event; later name changes retain canonical GUID provenance. Claude can implement this bounded screen on its own claimed branch. Primary reviews shared identity, financial joins and concurrency before integration.
